---
title: Scan for PII
description: Profile a dataset with STORM, review what it found, and turn the findings into an explicit masking pipeline.
---

STORM profiles a dataset before you write a masking pipeline: what fields
look like PII, which columns form a quasi-identifier group together, and a
re-identification risk score. It never masks anything and never applies a
pipeline on your behalf; it surfaces candidates for you to review. Run
against `decoy` CLI 0.1.0; every command block below is real output.

<Callout type="info" title="Suggestions, not classification">
STORM's detectors are heuristics. A finding is a candidate, not a verdict:
you read it, decide which mask strategy fits, and write that decision into
the YAML as an explicit `strategy:` entry. Nothing is masked until you do.
</Callout>

## 1. Scan the file

```console
$ decoy storm analyze customers.csv --out scan.json

╭─ decoy storm analyze ────────────────────────────────────────────────────────╮
│ Source        customers.csv                                                  │
│ Rows scanned  50 (head)                                                      │
│ Columns       8                                                              │
│ PII columns   4                                                              │
│ Reid risk     0.0                                                            │
│ Saved         scan.json                                                      │
│                                                                              │
│ Next:         decoy storm fields scan.json                                   │
╰──────────────────────────────────────────────────────────────────────────────╯
```

`--rows N --strategy random` caps and samples large files instead of
scanning everything; `--json` prints the full profile to stdout for piping
into other tooling.

<Callout type="warn" title="storm scan is deprecated">
`decoy storm scan` is the old name for this command. It still works today
(it prints a migration warning on stderr and runs `analyze` underneath) but
is scheduled for removal in 0.2.0. Use `decoy storm analyze`.
</Callout>

`--pii high --quasi` on `storm fields` narrows the list to fields that are
both high-PII and part of a quasi-identifier group, and `--json` pipes just
the matching field names to something like `jq`.

## 3. Turn findings into a pipeline

Passing the source file straight to `decoy init` scaffolds a pipeline from
the same STORM pass, with a `# REVIEW:` comment above every column it made a
call on:

```console
$ decoy init customers.csv --out pipeline.yaml -y

OK scaffolded pipeline.yaml from customers.csv
Next: read the # REVIEW: comments, edit as needed, then decoy validate config
pipeline.yaml
```

```yaml
# Decoy pipeline scaffold (column-aware).
# Generated by `decoy init customers.csv`.
# Read the # REVIEW: comments above each column before running.

tables:
  - name: data
    columns:
      # REVIEW: STORM detected multiple candidate signals (us_zip, mrn). The
      #   scaffolder picked truncate but the column may need a different
      #   strategy; review before running.
      - name: customer_id
        strategy: truncate
        provider_config:
          length: 3
      # REVIEW: STORM detected email addresses. Faker replaces with synthetic
      #   emails.
      - name: email
        strategy: faker
        provider: person_email
```

Every scaffolded column carries a `REVIEW` note explaining why STORM picked
that strategy, not a silent guess. Read them, change any strategy that is
wrong for your data, delete the comments, then validate and run:

```console
$ decoy validate config pipeline.yaml
OK pipeline.yaml
$ decoy run pipeline.yaml

╭─ decoy run ──────────────────────────────────────────────────────────────────╮
│ Pipeline  pipeline.yaml                                                      │
│ Mode      mask                                                               │
│ Elapsed   2.23s                                                              │
╰────────────────────────────────────────────────────────────────────────────╯
```

## 4. Check the result caught everything you meant to mask

`decoy storm integrity` runs the same post-mask checks the platform runs
when `run_storm: true` is set: residual PII, foreign-key preservation, and
policy validation against the config. Point it at the masked output and its
pre-mask source:

```console
$ decoy storm integrity customers.masked.csv --source customers.csv --config pipeline.yaml

                Storm integrity
                                               
 Bucket              Findings   Severities     
 ───────────────────────────────────────────── 
 residual_pii        3          fail:2, info:1 
 fk_preservation     0          clean          
 policy_validation   8          info:8         
                                               
pass=9  warning=0  fail=2  error=0
FINDINGS 2 fail/error findings; review the report.
```

Two `fail` findings, exit code `4`: the scaffolded strategies above
(`truncate` on `customer_id`, `redact` on names) still left something the
detector considers PII. That is the point of running this check, not a bug
in the recipe; the report names the exact column and detector so you know
which `# REVIEW:` line to revisit. It exits 0 when nothing is flagged and
`EXIT_FINDINGS` (4) whenever a column still carries real values through. See
[use Decoy in CI](/docs/how-to/use-decoy-in-ci) for wiring that exit code
into a build gate, and [STORM](/docs/concepts/storm) for why detection and
masking stay two separate, inspectable steps.
