# Product

## Register

brand

## Users

Decoy's public site and documentation serve developers, data engineers, privacy
teams, QA teams, and technical evaluators. The documentation must also work for
someone who is new to data masking and synthetic data generation. Their primary
job is to understand the intended Decoy workflow, complete a safe first run,
and then find exact configuration or command details without already knowing
Decoy's vocabulary.

## Product Purpose

Decoy helps teams turn sensitive source data into safer masked or synthetic
datasets. The public site explains the product family. The documentation teaches
the command-line workflow, explains where the platform fits, and provides an
accurate lookup surface for configuration, commands, operations, and technical
limits. Success means a new user can move from installation to a reviewed run
without searching for a highly specific answer first.

## Brand Personality

Calm, exact, and practical. The documentation should feel like a patient expert:
plain-spoken enough for a beginner, specific enough for a developer, and honest
about safety boundaries and product limits.

## Anti-references

- A scattered encyclopedia of isolated pages that only works when the reader
  already knows the exact term or command to search for.
- A raw command or schema dump presented as a user guide.
- Marketing-heavy documentation that hides the runnable workflow.
- An exhaustive beginner tutorial that makes experienced users follow a long
  sequence before they can reach reference facts.

## Design Principles

1. Teach the intended workflow before cataloging the available features.
2. Show commands in the order a user should run them and explain the purpose of
   each checkpoint.
3. Use one small, repeatable dataset across the first-run journey so progress is
   visible and examples compose.
4. Keep user guidance separate from exhaustive technical reference, while
   linking between them at the point of need.
5. State the boundary between the local CLI and the managed platform clearly.
6. Prefer verified examples, visible inputs and outputs, and explicit limits over
   abstract claims.

## Accessibility & Inclusion

Target WCAG 2.2 AA. Keep prose readable for people who are new to privacy and
data-engineering terminology, do not rely on color alone, support keyboard and
screen-reader navigation, preserve reduced-motion preferences, and make every
command sequence understandable without visual decoration.
