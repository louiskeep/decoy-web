By default, Decoy treats columns with many distinct values (>30) as free text during generation: it learns text length only, not vocabulary. For structured high-cardinality data like diagnosis codes or product SKUs, you can opt in to retain the full vocabulary and frequency distribution.

## The problem: high cardinality

A healthcare or retail dataset often has columns with thousands of distinct values:

- ICD-10 diagnosis codes: 74,000+ codes
- SKU or product codes: 10,000+ identifiers
- Customer IDs: millions of values

By default, Decoy's `fit` command detects these as high-cardinality and reclassifies them from categorical to freetext (length-preserving only). This is a safety measure: retaining 74,000 distinct values in memory requires significant resources and may not improve data utility.

For some datasets, this is fine. For others, you want the full vocabulary in the synthetic output.

## Opt in with high_cardinality: true

When generating a column, declare `high_cardinality: true` to force retention of all observed values:

```yaml
version: 1

global_settings:
  seed: 42

sources:
  claims:
    type: file
    format: csv
    path: ./claims.csv

tables:
  - name: claims
    row_count: 10000
    generate_columns:
      - name: diagnosis_code
        type: statistical
        high_cardinality: true
        allow_real_categories: true
```

With both flags set:
- `high_cardinality: true`: Force categorical, retaining all observed codes
- `allow_real_categories: true`: Preserve observed frequency (if code I10 appeared 50 times, it appears at roughly 50/n in the output)

## Limits and safety

Retaining high-cardinality vocabulary is memory-intensive. Decoy enforces two hard limits:

| Limit | Value | Why |
|---|---|---|
| Distinct values | 100,000 | Beyond this, memory use becomes prohibitive |
| Combined label size | 16 MiB | UTF-8 encoded labels cannot exceed 16 MiB total |

If your data exceeds either limit, the job fails with a typed error, not silent truncation.

Additionally, `high_cardinality` columns must be:
- String type (UTF-8 encodable)
- Non-ambiguous (no values that coerce to the same string under `str()`)

Numeric types (int, float) are rejected: use the `code_set` strategy for numeric codes.

## When to use it

Use `high_cardinality: true` for:
- Healthcare code sets (ICD-10, HCPCS, medical codes)
- Product SKUs or internal identifiers
- Structured billing or claim codes
- Domain-specific vocabularies under 100,000 distinct values

Do not use for:
- Free text (notes, descriptions, open responses)
- Numeric columns
- Columns with millions of distinct values
- When the observed frequency distribution is not representative (e.g., a sample of a much larger source)

## Configuration example

Masking and generation with high-cardinality healthcare codes:

```yaml
version: 1

global_settings:
  seed: 42

sources:
  claims:
    type: file
    format: csv
    path: ./claims.csv

tables:
  - name: claims
    columns:
      - name: claim_id
        strategy: passthrough
      - name: diagnosis_code
        strategy: code_set
        corpus: shipped:icd_10_cm
        allow_real_categories: true

  - name: procedures
    row_count: 5000
    references:
      - parent_table: claims
        parent_key: [claim_id]
        child_key: [claim_id]
    generate_columns:
      - name: claim_id
        type: reference
        reference_table: claims
      - name: procedure_code
        type: statistical
        high_cardinality: true
        allow_real_categories: true

targets:
  claims:
    type: file
    format: csv
    path: ./claims_masked.csv
  procedures:
    type: file
    format: csv
    path: ./procedures_synthetic.csv
```

## Interaction with differential privacy

High cardinality and differential privacy pull against each other. A DP fit
rejects `high_cardinality: true` and `allow_real_categories: true` outright,
because both release the full observed vocabulary instead of only the
thresholded labels a DP fit is allowed to emit.

What you can do instead is fit the column as a DP text carrier and let the
noisy threshold reduce it for you:

```console
$ decoy fit claims.csv --output claims.snapshot.json \
    --epsilon 1.0 --delta 1e-6 \
    --dp-text diagnosis_code \
    --dp-allow-omit
```

`--dp-allow-omit` lets the DP release cover `diagnosis_code` alone and leave
the other `claims.csv` columns out. Without it, every source column must be
declared with a carrier or the fit refuses.

A `--dp-text` release keeps only the categories whose noisy count clears the
threshold and drops the rest, so a 74,000-category column comes back as the
common codes alone. You do not list a subset by hand; the threshold does the
reduction. The tradeoff is built in: the frequent categories survive with a
budgeted guarantee, and the long tail does not appear. Use this when a formal
privacy guarantee matters more than covering every rare value. For the full
mechanism, see [Differential privacy in Decoy](/docs/concepts/differential-privacy).

## Troubleshooting

**Error: `code_set_corpus_too_many_values` or similar**

Your vocabulary exceeds 100,000 distinct values. Options:

1. Set `high_cardinality: false` (default) to reclassify as freetext
2. Use `allow_real_categories: false` to collapse rare values into `__other__`
3. Filter your source to a representative subset

**Output loses rare categories even with `high_cardinality: true`**

This happens with `allow_real_categories: false` (the default). Set `allow_real_categories: true`:

```yaml
- name: diagnosis_code
  type: statistical
  high_cardinality: true
  allow_real_categories: true
```

**Memory error during generation**

Your vocabulary is too large or the combined UTF-8 size exceeds 16 MiB. Try:
- Reducing the source dataset size
- Using a reduced category list
- Setting `allow_real_categories: false` to collapse tail categories
