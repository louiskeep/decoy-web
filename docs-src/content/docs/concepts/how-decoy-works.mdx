---
title: How Decoy works
description: Understand the shared workflow behind masking and synthetic data generation.
---

Decoy turns a reviewed pipeline configuration into a reproducible data job. The
configuration states what Decoy reads, what it changes, and where it writes the
result.

## The workflow

```text
source or generation rules
          |
          v
       Pre-scan
          |
          v
reviewed pipeline configuration
          |
          v
validate and preflight
          |
          v
 compile, then Transform
          |
          v
       Post-scan
          |
          v
 output, checks, evidence
```

Each stage has a different purpose. A pre-scan provides information. The
pipeline records the user's decisions. Validation rejects invalid work.
Transform creates the output. Post-scan checks measure specific output
properties.

The three data phases make different claims. A pre-scan reports detection
candidates and never shows that an output is safe. Transform applies your
reviewed rules. Post-scan reports integrity findings and measured fidelity;
neither is a release decision, and fidelity is not a privacy guarantee. A
pipeline runs the integrity checks only when `post_scan.integrity` is set to
`true`; otherwise you run them as separate commands.

## CLI and platform

The CLI runs local files from a local pipeline configuration. It is suitable
for development, test fixtures, and CI jobs.

The platform uses the same pipeline model. It adds saved connectors, access
controls, shared job history, reviews, schedules, triggers, and operational
records.

## Review stays explicit

Decoy can suggest possible sensitive fields and starter strategies. These
suggestions are not final classifications. A user reviews the configuration
before a run.

This boundary keeps the decision visible. It also makes the pipeline suitable
for source control and review.
